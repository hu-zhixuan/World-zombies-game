# 重做架构：v57 从头搭

> 写给接手执行的人。作者的判断是：**现在的版本方方面面都丑，只有玩法、思路、剧情值得保留。**
> 所以 v57 不是在旧代码上翻新，而是新搭一套，把玩法和剧情搬过去。
> 「做成什么游戏」看 `redesign_proposal.md`（已拍板，不变）；这份讲「用什么搭、怎么分层、长什么样、按什么顺序做」。

## 1. 结论：重写，不翻新

| 留下 | 扔掉 |
| --- | --- |
| 玩法规则和已拍板的重构方向（`redesign_proposal.md`） | 全部旧代码（搬去 `legacy/` 只当参考） |
| 剧情和所有文案：对白、Boss 台词、章节卡、图鉴描述、菜名、武器名 | 全部画面：代码画的小人、emoji 图标、每个弹窗各写各的样式 |
| 数值目标（击杀时间 0.6～1.2 秒、星级倍率、血量曲线） | 已拍板要砍的系统（梦境、远征、两套改装、升级弹天赋、职业神兵……） |
| 手机瞄准的设计（自动锁定 + 拖动瞄准 + 脚下红圈） | 防卡死看门狗（新架构从结构上不需要它，见第 5 节） |
| 踩过的坑（`CLAUDE.md`）和真实触摸测试的方法 | |

为什么不在旧代码上改，数据如下：

- 28,000 行 JS 全在一个全局作用域里，约 20 个系统互相直接改对方的变量；其中一多半系统本来就拍板要砍或合并。
- 画面是 2,820 行手写的画布绘图指令加 emoji；界面有 520 处行内样式、1,083 种不同的颜色值、80 种字号、42 层 z-index。这种状态下没法「统一一下风格」，只能重画。
- 换美术 = 重写全部绘图代码；按方案改玩法 = 重写大部分系统代码。两件事加起来，旧代码剩不下多少，却要继续背着它的全局变量和补丁。

## 2. 现在为什么丑（照着截图看出来的）

这几条直接对应第 3 节的规矩，执行时拿来对照：

1. **三套画风混在一起**：顶栏是细线图标，商店是 emoji 加半透明深色卡片，战场是代码画的小人。
2. **画面大半是空的黑**：主角只占屏幕高度的十分之一左右，战场上一大片深色空地和一堵灰墙。
3. **字又多又小**：画布里直接写小字（餐厅顶上那行说明在手机上根本看不清），商店一屏十几张卡片全是说明文字。
4. **不贴合手机屏幕**：餐厅两边是黑边，下半屏是空地板。
5. **没有打击感的层次**：打中、击杀、升级，反馈都差不多。

## 3. 画面规矩

作者给的参考是《潜水员戴夫》和《元气骑士》，两个都是像素风，所以方向定为**像素风**。先出效果图让作者确认（见第 7 节 M1），确认前不要大量铺内容。

**画布**
- 逻辑高度固定 270 像素，宽度随手机比例在 480～640 之间变，铺满屏幕，**不留黑边**。最近邻放大，不要模糊。
- 主角约占画面高度的六分之一（40～48 像素高），僵尸同级。镜头要近，画面里要有东西。

**颜色**
- 全游戏只用一套调色板，不超过 32 色（选一套公开的像素调色板，定下来就写进代码当常量）。界面和画面用同一套。
- 白天战场偏暖的黄昏色，夜晚食堂是暖灯光。用色相区分昼夜，而不是把整屏压黑。

**素材**
- 禁止用 emoji 当图标或美术。图标统一一张 16×16 的图标表。
- 来源优先级：先找 CC0（可自由使用）的像素素材包，统一重新上色到调色板；缺的再用同一调色板按像素格补画。每份素材的出处和许可记在 `assets/CREDITS.md`。
  这个环境里 opengameart.org、itch.io 能访问，kenney.nl 被拦（403）。
- 所有画面元素通过「素材键」引用（比如 `zombie.roamer.walk`），素材打成图集。以后换一套美术只换图集，不动代码。

**界面**
- 文字全部用网页元素显示，不往画布里写字（画布放大后中文会糊）。最小字号 12px。先用系统字体加粗，像素字体以后再说。
- 一份设计常量（`ui/tokens.css`）：间距 4/8/12/16，字号 4 档，圆角 2 档，层级只有 4 层（世界 / 顶栏按键 / 面板 / 提示）。颜色只能取自调色板。
- 只有一套面板、一套按钮（主要 / 普通 / 危险三种）、一套卡片。所有弹窗都用它们拼，不许各写各的。风格要「实心色块 + 粗描边」的厚实感，不要半透明毛玻璃。
- 一屏只讲一件事：卡片上放图标、名字、一个关键数字，详细说明点开再看。
- 加一条自动检查：`ui/` 里出现行内样式或调色板以外的颜色值，测试就失败。规矩靠机器守，不靠自觉。

**手感（最少要有的反馈）**
- 命中：目标闪白 + 小幅击退 + 伤害数字。击杀：碎裂 / 消散动画 + 掉落物弹出。
- 开火：枪口火光 + 轻微后坐。重武器和 Boss 攻击才有屏幕震动，幅度要小。
- 升星、三选一、过关：各有一个明显不同的演出。

## 4. 技术栈（已验证能跑）

| 用途 | 选择 | 说明 |
| --- | --- | --- |
| 语言 / 构建 | TypeScript + Vite | 有模块、有类型，告别全局变量 |
| 画面引擎 | Phaser 3.90.0（锁死版本） | 场景、图集、动画、镜头、粒子、缩放都是现成的。npm 上最新是 4.x，没验证过；重做期间不要升级 |
| 面板和顶栏 | Preact | 界面跟着状态自动更新，不再手拼 HTML 字符串 |
| 测试 | Vitest | 规则层不依赖浏览器，直接跑 |
| 打包 | vite-plugin-singlefile | 产物仍是**一个 HTML 文件**，图集内嵌 |

验证结果：按上面的组合做了一个最小样例，打出来是 1.2 MB 的单个 HTML（旧版 1.5 MB），在手机尺寸、安卓 WebView 标识的浏览器里用 `file://` 直接打开能跑，零报错；规则层的测试不开浏览器就能跑。

因为产物还是单个 HTML，**安卓壳和发版流程基本不用动**：壳还是加载 `file:///android_asset/index.html`，只需要把 `tools/copy_to_android.js` 的来源路径、CI 和 release 工作流里的安装与构建命令改成新的（`npm ci`、`npm test`、`npm run build`，并提交 `package-lock.json`）。

离线要求：APK 里不能联网取任何东西。字体、素材、引擎全部打进那一个文件。

## 5. 分层（这是整套架构的核心）

```
src/
  content/   数据：武器、僵尸、塔、天赋、菜谱、职业、剧情文本。只有数据，没有逻辑
  sim/       规则：纯 TypeScript。不碰 Phaser、不碰网页、不用 Math.random 和系统时间
  view/      Phaser 场景：照着规则层的状态把画面画出来，听事件播特效和音效
  ui/        Preact：顶栏、触屏按键、所有面板
  app/       启动、存档、音频、把上面几层接起来
```

**规矩，一共六条：**

1. **规则层自己能跑完一整局。** 固定每秒 60 步，随机数用带种子的生成器。输入是「指令」（移动、开火、买塔、选天赋），输出是「状态」和「这一步发生的事件」。
   好处：不开浏览器就能测数值；能写一个自动打的机器人跑完 15 天，直接量出难度曲线和「塔会不会自己把怪清光」。旧版改伤害公式没有任何测试能兜底，就是因为规则和画面搅在一起。
2. **画面层和界面层只读状态、只发指令**，不直接改状态。
3. **一局的全部状态是一个对象**（`RunState`），能直接转成 JSON。存档就是把它存下来，读档就是读回来。不再一个字段一个字段地手写存读。
   局外成长（星星、已解锁内容）是另一个对象（`MetaState`），存在另一个键下，重开一局不动它。
4. **流程是一台明确的状态机**：白天 → 清场 → 据点 → 夜晚 → 结算 → 下一天（以及 Boss、死亡、通关）。面板用一个「面板栈」统一管，游戏是否暂停只看栈里有没有东西。
   旧版的卡死全是这一类问题：十几个「是否打开」的开关各管各的，再加一个看门狗猜是不是卡住了。新架构里同一时间谁在最上面只有一个答案，不需要看门狗。
5. **伤害只有一个入口**，能乘的倍率写死在那一个函数里：武器基础 × 星级 × 今天的菜 × 临时状态。光灵、伙伴、载具走各自的入口，不吃武器星级。
6. **天赋和星级特效写成数据**（挂在哪个时机、什么效果、什么参数），由一小组通用效果实现。不要再出现「每个天赋在十几个地方各判断一次」。

实体不需要引入 ECS 之类的框架：僵尸、子弹、塔就是普通对象的数组。这个游戏的物理很简单（僵尸沿地面线走，子弹是直线或抛物线），碰撞在规则层里自己算，不用 Phaser 的物理引擎。

## 6. 调试和测试

- **数值测试**（Vitest）：「跟得上进度」的武器打普通僵尸，1～15 天击杀时间都在 0.5～1.5 秒；捡到同名武器升星；存档读写前后状态一致。
- **机器人跑局**（Vitest）：固定种子，自动打完 15 天，断言每天的通关用时、掉血量、塔的击杀占比在合理范围。调数值时先看它。
- **真实触摸**（Playwright，沿用 `tools/e2e/` 的做法）：手机尺寸、安卓 WebView 标识，用 CDP 发真实触摸事件走完整一轮。新代码没有全局变量，所以要在调试构建里挂一个 `window.__game`，让脚本能读状态。
- **截图对照**：每个里程碑固定截同一组画面（战斗、三选一、工坊、据点、食堂），放进 PR 里，前后对比。画面改动必须看图，不能只看测试通过。
